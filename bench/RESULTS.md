# vue-zero vs Nuxt 4 (CSR) 측정 결과

> 목적: "Nuxt 4 CSR을 따라가긴 힘들지만 중소규모 앱에서는 훨씬 더 효과적인 프레임워크가 되길 원한다" — 어디서 이기고 지는지 수치로 확인한다.
> 원칙: **실측과 추정을 구분**한다. 표의 모든 수치는 `results/*.json`에서 추적된다(출처 열/각 표 머리말의 `cells["규모|프로필|변형"]["지표"]` 키). 측정하지 않은 것은 주장하지 않는다. 결과가 vue-zero에 불리해도 그대로 적었다.

## 2. 이기는 곳 / 지는 곳 / 비슷한 곳

**이기는 곳 (실측)**
- 콜드 요청 수: 홈 기준 vz 15/17/19개(S/M/L) vs Nuxt 23/25/25개 (`cold.requests`, 전 프로필 동일).
- 콜드 전송 바이트: vz 79,879/80,988/82,187 B vs Nuxt 80,568/84,415/91,816 B (P1). L에서 -10%.
- 미방문 페이지 이동 시 **요청 수·바이트**: M 기준 20연속 이동 총 요청 99 vs 152, 66,573 B vs 78,338 B (`nav.seq_total_*`, P1).
- 네트워크 지연이 없는 환경(P1)의 첫 이동·연속 이동: vz 43.5ms vs Nuxt 57.5ms (M, `nav.seq_avg_ms`).
- 툴체인: 앱 개발자 설치 0·빌드 0·설정파일 0 (§3.5).

**지는 곳 (실측)**
- RTT가 있는 환경의 콜드 로드: P2에서 436 vs 252ms(M), P3에서 1,657 vs 1,080ms(M). 원인은 요청 수가 아니라 **직렬 요청 단계(워터폴) 수** (§4).
- **웜(재방문) 로드**: P2 380 vs 76ms, P3 1,283 vs 269ms(M). vz는 해시가 없어 매 방문 15~19개 재검증 요청(304)을 보낸다 (`warm.requests`, `warm.n304`).
- RTT 있는 환경의 첫 이동·연속 이동(M·L): P3 첫 이동 543 vs 302ms(M), 연속 평균 478 vs 272ms.
- 한 페이지가 쓰는 컴포넌트가 많아질 때: 홈이 컴포넌트 노드 92개(X60)/228개(X150)면 vz 요청 70/160개 vs Nuxt 19/17개, P3 ready 1,898/2,589 vs 1,050/1,085ms (§3.4).
- 메모리: 이동 후 힙 +7~13%(L: 5.2 vs 4.6MB), `<style>` 노드 154개(L) vs Nuxt `<link>` 129개(별개 구조).

**비슷한 곳**
- P1 콜드(차이 5~15ms, 노이즈 수준), 콜드 바이트(S/M), 재방문 이동, DOM 노드 수, 이벤트 리스너 수(L: 152 vs 154), 런타임 컴파일 CPU(§4: 홈 콜드 TaskDuration 차 P1 +5~10ms).

## 4. 분석: 왜 그런가

1. **병목 #1 — 직렬 요청 단계(워터폴).** `results/waterfall.json`(M, P3 네트워크, CPU 1x, 각 3회): vz는 **7개 웨이브**(index.html → 라이브러리 3개 → manifest 2+404/error 프로브 → `pages/index.vue` → 컴포넌트 → 중첩 컴포넌트 → **`layouts/default.vue`(맨 마지막)**), Nuxt는 **4개 웨이브**. 웨이브는 "시작 시각 간격 > RTT/2"로 군집화한 타이밍 기반 추론이다. ready 격차(P3 약 570ms, P2 약 180ms)는 약 3.8(P3)~4.6(P2) RTT에 해당하는 크기다(RTT 150/40ms, 대역폭 영향 포함). 요청 수·바이트는 오히려 vz가 적다 — 즉 격차는 크기가 아니라 **지연 × 단계 수**다. 홈 페이지만 해당하므로 규모 S→L에서 거의 늘지 않는다.
2. **병목 #2 — 재검증 요청 수.** 해시가 없는 파일은 `max-age=0, must-revalidate` → 재방문마다 홈이 쓰는 파일 전부에 조건부 요청(15~19개 304). 바이트는 ~500B지만 웨이브 구조(위 1번)를 그대로 되풀이해 P3 웜 1.28초(Nuxt 0.27초). Nuxt는 `/_nuxt/*`가 immutable이라 요청 1개(HTML 재검증)뿐.
3. **병목 #3 — 컴포넌트당 요청 1개.** 컴포넌트 수에 비례해 요청이 늘고(X150: 160개) 개별 `.vue` fetch + 런타임 파싱/컴파일 비용이 붙는다. X60→X150 구간 증가분(요청 +90): P1 +43ms(≈0.48ms/컴포넌트), P3 +691ms(≈7.7ms/요청). Nuxt는 같은 구간 +34ms(P3) — 한 청크로 묶이기 때문(`cold.requests` 19→17).
4. **런타임 컴파일 CPU는 이 앱 크기에서는 지배적 병목이 아니다.** 홈 콜드 `Performance.getMetrics` TaskDuration 중앙값: P1 vz 36.3/40.4/44.9ms vs Nuxt 31.5/31.1/34.6ms(S/M/L), P3(CPU 4x) vz 171.5/177.3/191.1 vs 145.5/135.4/147.1ms. 차이는 +5~10ms(P1)/+26~44ms(P3)로, 콜드 격차(수백 ms)의 대부분을 설명하지 못한다. 컴포넌트가 수십 개로 늘면(X150: P1 113 vs 47ms) 의미 있어진다. **(해석상 주의: ScriptDuration은 양쪽 3~25ms라 컴파일/파싱 비용을 따로 분리하지 못했다 — 컴파일 비용의 정확한 몫은 미측정, 추정)**
5. **미방문 이동**: P1에서 vz가 빠른 것은 Nuxt가 페이지당 CSS·JS 파일 10~12개를 가져오는 반면(`nav.first_requests`) vz는 5~7개이기 때문이다(지연 0에서는 요청 수가 지배). RTT가 생기면 vz의 직렬 단계(page → comps → nested comps)가 지배해 역전된다.
6. **메모리**: vz는 페이지·컴포넌트별 `<style>` 노드를 남기고(L 154), 컴파일된 render 함수·SFC 캐시를 유지해 힙이 7~13% 크다(원인 분해는 미측정 — 추측).
7. **재방문 이동이 동률인 이유**: 두 프레임워크 모두 이미 로드된 JS 모듈을 재사용하는 순수 클라이언트 라우팅이고 측정 하한(2 rAF)에 걸린다.

## 5. 개선 여지 (우선순위순)

**Top 1. 요청 워터폴 단축 — 힌트/병렬화 (측정됨).** 라이브러리 수정 없이 `index.html`에 `<link rel="preload" as="fetch" crossorigin>` 힌트만 넣어 시험했다(M, 각 7회, `results/hints.summary.json`; 요청 수 17 그대로 → 중복 요청 없음).

| 변형 | 힌트 내용 | P2 콜드 | P3 콜드 | P2 웜 | P3 웜 |
|---|---|---|---|---|---|
| vz | 없음 | 429.4 | 1,674.1 | 375.8 | 1,291.3 |
| vz-hintsA | pages.json·components.json·layouts/default.vue·pages/index.vue | 344.5 (-20%) | 1,349.5 (-19%) | 269.9 | 932.5 |
| vz-hintsB | A + 홈이 쓰는 컴포넌트 전체(중첩 포함) | 248.4 (-42%) | 1,072.6 (-36%) | 173.6 | 609.6 |
| vz-hintsB-imm | B + 전 파일 immutable | 248.5 | 1,067.0 | 80.7 | 298.2 |
| nuxt | — | 254.9 | 1,096.4 | 74.2 | 270.5 |

(같은 실행 묶음 내 비교. load avg 9.0~20.8, 중앙값 12.7로 가장 시끄러운 묶음 — 변형이 인터리브되어 있어 상대 비교는 유효하나 절대값은 main과 다소 다르다.) 힌트 B는 "홈이 쓰는 파일 목록을 빌드 시점에 아는" 이상적 상황이므로 **상한에 가깝고 홈 한 페이지에만 해당**한다. 실제 이득은 A~B 사이이며, 일반화하려면 라이브러리/`scan` 쪽에서 구현해야 한다(미구현·미측정). 구현 후보와 **추정**(측정 아님): (a) `layouts/default.vue`를 페이지 fetch와 병렬로 선요청 → 웨이브 1개 감소(≈1 RTT, P3 약 150ms), (b) manifest를 라이브러리 스크립트와 병렬로 선요청 → 웨이브 1개 감소(힌트 A가 둘+α로 -19%를 보인 것과 일치). 

**Top 2. 파일 해시 + 장기 캐시 (vz-immutable, 상한 시뮬레이션).** `vz-immutable`은 **실제 구현이 아니라** "scan이 파일 해시를 URL에 넣어 immutable로 서빙했을 때"의 **이득 상한 추정**이다(index.html 포함 전부 immutable로 서빙하므로 HTML 갱신 전파 문제는 무시한 값). 웜 ready: P2 379.6→83.9ms(-78%), P3 1,282.8→300.8ms(-77%)(M)로 Nuxt(75.9/268.8)와 ±12% 이내, 웜 요청 17→2개. 콜드는 변하지 않는다(`cold.ready_ms` vz-immutable ≈ vz). 남는 2개는 404/error 프로브.

**Top 3. 불필요한 요청 제거 — 404/error 프로브 2개(추정).** `src/vue-zero.ts`(createApp 초기)에서 두 존재 확인 fetch가 무조건 실행된다(코드 읽기로 확인). 콜드 요청의 11~13%이고 404는 `no-store`라 웜에서도 제거되지 않는다. pages.json에 `404`/`error`가 있는지로 대체하면 요청 2개 감소(시간 이득은 병렬 웨이브라 작을 것으로 추정 — 미측정).

기타 후보(모두 미측정·추정): 컴포넌트 수가 많은 페이지(X60+)는 개별 요청이 지배하므로 빌드 없는 범위 안에서는 "페이지 단위 선택적 번들"이 유일한 구조적 해법이나 제로빌드 철학과 충돌한다 — 철학상 비채택, 대신 §7의 기준선으로 사용 범위를 제한하는 편이 현실적. Nuxt의 `NuxtLink` 프리패치에 해당하는 기능(링크 가시성 기반 선로딩)은 연속 이동 격차(M·L P3 1.7x)를 줄일 수 있다(추정).

## 6. 공정성 한계와 미검증

- **같은 코드의 Nuxt 쪽 조건**: `<router-link>` 사용(NuxtLink 프리패치 없음, 소스를 동일하게 유지하기 위한 선택). 실제 Nuxt 앱은 NuxtLink를 쓰므로 Nuxt의 이동 지연은 실사용에서 더 작을 수 있다(미측정).
- 콜드/웜은 **홈 페이지 한 곳**만 측정(딥링크 진입은 미측정). 전체 페이지 수(S→L)는 콜드 시간에 거의 영향이 없고, 영향 변수는 "페이지당 컴포넌트 수"다(§3.4).
- Nuxt는 데이터 fetch·상태·플러그인·이미지·폰트 없음, SFC당 약 4~5KB. 실제 앱(외부 API 지연, 이미지, 폰트, 서드파티)에서는 두 프레임워크 공통 비용이 커져 상대 격차가 줄어든다(추정).
- 로컬 루프백 + CDP 스로틀링(RTT/대역폭/CPU 배수). 실제 CDN·TLS 핸드셰이크·패킷 손실·HTTP/3 미반영. CF는 사전 압축 + h2/h3이다(서버 첫 요청 압축은 예열로 제거). 자체서명 인증서는 `--ignore-certificate-errors-spki-list`로 신뢰시켜 캐시가 정상 동작함을 웜 측정(Nuxt 24~26 캐시 적중)으로 확인.
- 노이즈: load avg 6~21(§0). P1 값(수십 ms)은 노이즈에 가장 민감. p90은 summary.json 참조.
- 헤드리스 셸 Chromium만(Safari/Firefox/실기기 미검증). CPU 4x는 메인 스레드 스로틀이며 실제 중저사양 기기의 메모리/GC 특성과 다르다.
- vz 컴파일 CPU의 정확한 비중, 메모리 차이의 원인, 장시간 사용 시 누수는 미측정. TBT/INP/long task 미측정. 시각적 완성도(레이아웃 시프트) 미측정.
- **개발 루프 지연(저장→화면 반영, HMR vs 새로고침)은 측정하지 않았다**: 시스템 노이즈 하에서 파일 감시·HMR 타이밍이 불안정할 것으로 판단해 선택 항목이라 생략(측정한 것은 개발 서버 기동 시간뿐).
- `nuxt dev` 첫 화면 도달 시간(vite 첫 컴파일 포함) 미측정. vz 개발 서버는 일반 정적 서버라 별도 기동 개념이 약하다.
- `vz-immutable`/`vz-hints*`는 상한/가능성 확인용 시뮬레이션이다(실제 구현 아님, hintsB는 홈의 정확한 파일 목록을 아는 이상적 경우).
- 본 측정 후 러너에 보조 옵션(`--cold-only`, 힌트 변형, `--index-file`)을 추가했다. 기본 경로(변형 vz/vz-immutable/nuxt)의 코드는 본 측정과 동일하다.

## 7. "중소규모 앱" 기준선 제안 (데이터 근거)

측정 범위 안에서 vz의 불리함은 **총 페이지 수가 아니라 페이지당 컴포넌트 fan-out(요청 수)과 RTT**에 좌우됐다. 따라서 규모를 이렇게 정의하는 것을 제안한다(L = 150페이지/300컴포넌트까지가 **실측 범위**이며 그 위는 미검증).

| 구간 | 기준(제안) | 근거(실측) |
|---|---|---|
| 중소규모(vz 권장) | 페이지 ≤ 150, 전체 컴포넌트 ≤ 300, **페이지당 중첩 포함 컴포넌트 ≤ ~10~15개**(요청 ≤ ~20/페이지), 사용자가 주로 지연이 낮거나(P1~P2) 재방문이 적은 환경 | L(15노드 최대)에서 콜드 1.43~1.54x(P3)로 일정, 규모 확대로 악화되지 않음(§3.1) |
| 주의 | 페이지당 컴포넌트 ≳ 30~60개 또는 대부분 사용자가 P3급 네트워크 | X60: P3 콜드 1.81x, 요청 70개; X150: 2.39x(P3), 160개(§3.4) |
| Nuxt 권장 | 페이지당 컴포넌트 100+, 재방문 많은 장수 사용자 앱(해시 캐시 없이는 웜 4~5x 차), 첫 로드 성능이 KPI | X150, §3.2 |

개선 후(Top 1·2 적용 가정)의 근거: 힌트 B+immutable 변형이 M 홈에서 콜드 ±3%·웜 +10% 이내로 Nuxt에 수렴했다(§5). 따라서 "중소규모에서 Nuxt와 동급 이상" 목표는 **라이브러리/scan 개선(요청 단계 병렬화, 해시 캐시)이 전제**일 때 데이터상 달성 가능성이 있다 — 현 v1.3.1 단독으로는 RTT가 있는 환경의 콜드·웜·연속 이동에서 지며, 이기는 곳은 요청 수·바이트·툴체인 단순성·지연 없는 환경이다.

임계값을 CI에서 회귀 방지하는 방법: §8과 `bench/budget.json`.

## 9. v1.5.0 개발 중 측정: 매니페스트 + 영속 캐시 (`vz-manifest`)

> 측정 시점: v1.5.0 개발 중(미릴리스), package HEAD 177f8f0 이후 로컬 커밋 + 작업 트리의 dist. 데이터: `results/compare.json`(원시, 반복별 값 포함), `results/compare.tables.md`. 재현: `node bench/compare.mjs`(약 4분). **요청 수·바이트·.vue 수·웨이브만 판정 근거**이고 시간(ms)은 참고용이다.

### 9.1 변형과 측정 방법
- `vz-manifest` = `VueZero.createApp({ manifest: true })` + `vz-manifest.json`(테스트 전용 생성기 `test/scripts/gen-manifest.mjs` 출력) + Cache Storage 영속 캐시. 서버는 `vz` 와 같은 cf 모드(`max-age=0, must-revalidate`): **서버 캐시 설정에 의존하지 않는다.**
- **prod 호스트 판정**: 라이브러리는 `127.0.0.1`/`localhost`/`[::1]`/`?vzdev` 를 dev 로 보고 영속 캐시를 끈다. 러너는 이 변형만 `https://vzm.bench.test:<port>` 로 접속하고 Chromium `--host-resolver-rules="MAP *.bench.test 127.0.0.1"` 로 로컬 서버에 매핑한다(자체서명 인증서는 SPKI 신뢰라 호스트명 무관, https 라 보안 컨텍스트). 검증: 이 호스트를 `127.0.0.1` 로 바꾸면 웜 .vue 가 9건으로 되돌아가 게이트가 실패한다(§9.5). `--h1`(평문 http)에서는 비보안 컨텍스트라 `caches` 가 없어 폴백(= 영속 캐시 효과 없음)된다.
- 요청 수 = 네트워크를 탄 요청(304 포함, HTTP 메모리/디스크 캐시 적중 제외). Cache Storage 적중은 네트워크 이벤트가 없어 제외된다. 웨이브 = 요청 시작 간격 > RTT/2(75ms) 군집(RTT150 에뮬, 대역폭 무제한; **타이밍 기반 추론이며 실제 의존 관계가 아님**). 반복 3회 모두 값이 같았다(표는 min~max, 같으면 단일 값).
- 홈 페이지 한 곳의 콜드(새 컨텍스트) → 웜(같은 컨텍스트 새 탭). 규모별 홈의 .vue 수는 S 7 / M 9 / L 11.

- 이 표의 `vz` 는 404/error 지연 확인(b86d78e) 적용 후라 v1.4.0 기준선(M 콜드 17)보다 요청이 2건 적다. v1.4.0 대비 M 콜드는 17 → 14, 웜 17 → 5, 웜 .vue 9 → 0, 웨이브 7 → 4.
- 콜드 전송 바이트: vz-manifest 가 vz 보다 큰 이유는 라이브러리(dist 19,668 B, v1.4.0 17,146 B 대비 +2,522 B)와 매니페스트(`files` 해시·`deps` 포함, L 에서 가장 큼)다. 콜드 바이트는 개선 항목이 아니다.
- 웜 5건의 정체(M, `results/compare.json` 의 `paths`): `/`(HTML) + `/lib/vue.js` + `/lib/vue-router.js` + `/lib/vue-zero.js` + `/vz-manifest.json`, 모두 304 재검증. 규모와 무관하게 5.
- Nuxt 콜드 요청이 많은 것(23~25)은 청크 분할 때문이며 웨이브는 3.

### 9.3 목표 대비 (정본 목표)

| 목표 | 결과 | 판정 |
|---|---|---|
| 규모 M 웜 재방문 .vue 요청 0건 | 0 (S/M/L 모두) | 달성 |
| 웜 전체 요청 ≤ 3건 (HTML + 매니페스트 + 라이브러리 재검증) | **5건** | **미달** |
| 첫 방문 요청 -2건 이상(404/error) | vz(매니페스트 off) 17 → 15 (-2, 404 확인 제거). 매니페스트 on 은 추가로 -1 → 14 | 달성 |
| 직렬 단계 vz 7 → 5 이하 | M 7 → 4 (웜은 7 → 3) | 달성 |

**웜 ≤3 미달의 원인과 한계**: 목표의 "라이브러리 재검증"은 1건으로 가정했지만 이 앱은 `vue.js`·`vue-router.js`·`vue-zero.js` 3개를 `<script src>` 로 로드하고, 서버가 `max-age=0, must-revalidate`(Cloudflare 정적 자산 기본 모사)라 3개 모두 매 방문 304 재검증을 한다 → HTML 1 + 라이브러리 3 + 매니페스트 1 = 5. 라이브러리 요청은 `<script>` 태그가 만드는 것이라 vue-zero 가 줄일 수 없다(Service Worker·`_headers` 의존은 비목표). 5 → 3 이하로 가려면 앱/배포 쪽에서 라이브러리 URL 에 버전을 넣어 장기 캐시하거나(템플릿 `index.html` 의 몫) 한 파일로 묶어야 하며 이 벤치는 그 변형을 측정하지 않았다(미측정). 게이트는 현재 값 5 를 상한으로 걸었다(목표 3 으로 낮추지 않음).
